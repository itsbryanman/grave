# RFC-666: The GRAVE Volatile Retention Format

## Status of This Memo

This document specifies version 2 of the `.grave` container and the behavior required for interoperable implementations.

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this document are to be interpreted as described in RFC 2119.

## 1. Introduction

GRAVE is a deterministic container for decaying data. A `.grave` file stores:

- a versioned header,
- a compressed payload,
- a CRC32 of the original uncompressed payload,
- a CRC32 of the serialized header prefix.

Decay is a function of header state and time. Deterministic implementations render the same grave identically for the same header bytes and the same quantized day.

## 2. Terminology

- `Interment`: the initial creation of a `.grave` file.
- `The Deceased`: the original payload bytes.
- `Disturbance`: a header CRC mismatch.
- `Exhumation`: deterministic recovery of the original payload.
- `Terminal Decomposition`: a rendered decay state at or above `q = 9850`.
- `The Amber Clause`: read-only observation that leaves the header untouched.
- `Mourning`: a rate-limited action that resets neglect and increases half-life.

## 3. File Layout

All integer fields are little-endian.

### 3.1. Fixed Header Prefix

| Offset | Size | Field | Notes |
| --- | ---: | --- | --- |
| 0 | 8 | `magic` | `47 52 41 56 45 00 66 6F` |
| 8 | 2 | `version` | MUST be `2` |
| 10 | 32 | `burial_id` | render seed root |
| 42 | 8 | `buried_at` | unix timestamp, seconds |
| 50 | 8 | `last_opened` | unix timestamp, seconds |
| 58 | 4 | `open_count` | unsigned visit count |
| 62 | 1 | `rot_profile` | `0x01 mold`, `0x02 static`, `0x03 burnin`, `0x04 dataloss` |
| 63 | 1 | `flags` | bit 0 `hardcore`, bit 1 `mourned-recently` |
| 64 | 4 | `half_life_days` | unsigned |
| 68 | 4 | `mourn_credit` | unsigned, capped at `20` by the CLI and reference implementation |

The bytes from offsets `50..72` form the in-place patch window used by the reference implementation. Only `last_opened`, `open_count`, the `mourned-recently` flag, and `mourn_credit` are semantically mutable. `rot_profile` and `half_life_days` occupy the same contiguous write span but MUST remain unchanged after interment.

### 3.2. Variable Header Suffix

Immediately after offset `72`, the following length-prefixed UTF-8 strings appear in order:

1. `epitaph_len: u16`, then `epitaph` bytes
2. `original_filename_len: u16`, then `original_filename` bytes
3. `mimetype_len: u16`, then `mimetype` bytes

These are followed by:

- `original_len: u64`

The header CRC32 is computed over the entire serialized header prefix and suffix up to, but not including, the compressed payload.

### 3.3. Trailer

The payload and trailer follow the header:

1. `compressed_payload`
2. `payload_crc32: u32`
3. `header_crc32: u32`

`payload_crc32` is the CRC32 of the original uncompressed payload bytes.

## 4. Compression and Bounds

Implementations MUST bound decompression by the stored `original_len` and MUST reject any `original_len` greater than `512 MiB`.

The reference implementation uses zstd for native builds and `ruzstd` for wasm builds. Decoder output that exceeds `original_len` or stops short of `original_len` MUST be rejected.

## 5. Header Validation and Disturbance

If `header_crc32` does not match the serialized header bytes, the grave is disturbed.

Disturbance has these consequences:

- renderers MAY force maximum decay,
- visits and mourning MUST refuse to patch the file in place,
- exhumation MAY still succeed if payload decompression and `payload_crc32` validation succeed.

This behavior is the reference implementation's Disturbance Recovery rule: damage to the record does not automatically imply damage to the remains.

## 6. Deterministic Decay

### 6.1. Quantized Day Rule

Rendering MUST quantize `now` to whole UTC days before any branch-driving decisions are made. The reference implementation computes:

```text
age_days     = floor(now / 86400) - floor(buried_at / 86400)
neglect_days = floor(now / 86400) - floor(last_opened / 86400)
```

`grave inspect` MAY present a fractional intensity view. Renderers MUST NOT use that fractional path to decide output pixels or text.

### 6.2. Intensity

```text
effective_half_life_days = half_life_days * (1 + mourn_credit * 0.10)
base          = 1 - 0.5 ^ (age_days / effective_half_life_days)
neglect_boost = min(0.25, neglect_days / (4 * effective_half_life_days))
wear          = min(0.10, open_count * 0.002)
intensity     = clamp(base + neglect_boost + wear, 0.0, 1.0)
q             = floor(intensity * 10000)
```

`q` is the quantized intensity used to drive rendering.

Terminal decomposition occurs at `q >= 9850`.

### 6.3. Prognosis

`prognosis(header, now)` returns the earliest timestamp at which the quantized render path reaches terminal decomposition, assuming no future opens or mourning.

## 7. Visits, Mourning, and the Amber Clause

### 7.1. Live Visits

A live visit updates:

- `last_opened = now`
- `open_count += 1`
- `mourned-recently = false`

The reference implementation performs this as an in-place patch of the header window and then rewrites the trailing `header_crc32`.

### 7.2. Mourning

Mourning updates:

- `last_opened = now`
- `mourn_credit = min(mourn_credit + 1, 20)`
- `mourned-recently = true`

Mourning is rate-limited. If `mourned-recently` is set and `now - last_opened < 7 * 86400`, a second mourning action MUST be treated as a no-op.

### 7.3. The Amber Clause

Read-only observation is permitted. If a grave cannot be patched because the filesystem is read-only or the observer is read-only by design, the payload MAY still be rendered. The stored header remains authoritative until a writable visit occurs.

The web viewer is an Amber Clause observer: it never writes.

## 8. CLI Time Semantics

The reference CLI's `--at YYYY-MM-DD` semantics are normative for compatible frontends:

- the provided date is interpreted as `23:59:59 UTC` on that calendar day,
- the grave is rendered for that timestamp,
- no visit patch or hardcore rewrite occurs.

Dates earlier than `buried_at` MUST be rejected.

## 9. Rot Profiles

### 9.1. Mold (`0x01`)

- Images use an `8x8` cell grid, deterministic row-major day stepping, and an annual cap of `365` simulated growth days.
- Image growth is biased by a seeded low-frequency field so colonies advance anisotropically, and image compositing desaturates toward local luminance before tinting so the mold treatment stays recognizable across different base hues.
- `age_days` is a direct render input and MUST be the quantized render age.
- Text preserves whitespace structure and progresses through `▒` and `▓` overgrowth.

### 9.2. Static (`0x02`)

- Images apply pixel noise, block corruption, scanline tears, and brightness drift.
- Text applies substitutions, echoed lines, and carrier-loss truncation.

### 9.3. Burn-in (`0x03`)

- `open_count` is a direct render input.
- Images composite up to `12` ghost copies, reduce contrast toward the mean luminance, shift toward sepia, and apply vignette plus hotspot.
- Text echoes the first line once per three opens, up to eight echoes, and fades body characters over time.

### 9.4. Data Loss (`0x04`)

- Images kill clustered `32x32` blocks, then escalate to row loss and unrecoverable labels.
- Text deletes clustered sentences and paragraphs and reports lost section counts.

## 10. Hardcore Mode

Hardcore mode is signaled by flags bit 0.

On a live hardcore open:

1. the grave is rendered,
2. the rendered output becomes the new payload,
3. the file is rewritten atomically via temp-file-then-rename,
4. `buried_at` remains unchanged.

Hardcore exhumation MUST be refused.

Terminal hardcore graves remain terminal. There is no recovery path in the reference implementation.

## 11. Security Considerations

A `.grave` file is a container of untrusted data and grief.

Implementations:

- MUST validate `magic` and `version`,
- MUST bound decompression by `original_len`,
- MUST reject `original_len > 512 MiB`,
- MUST verify `payload_crc32` before claiming successful exhumation,
- SHOULD treat header CRC failure as disturbance rather than blindly trusting mutable metadata.

## 12. Interoperability Notes

The reference implementation currently ships:

- native CLI in Rust,
- browser-facing wasm bindings in Rust,
- a static viewer under `viewer/`,
- deterministic golden render tests for native and wasm.

Future format versions MUST bump `version` and MUST NOT silently reinterpret version 2 graves.
